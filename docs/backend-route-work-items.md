### A. 선택 경로 QR

현재 프론트는 조회 성공 시 출발·도착 좌표로 카카오맵 길찾기 주소를 만든다. 따라서 후보별 주소 누락만으로 QR 오류가 발생한다고 단정할 수 없다. 조회 직후 선택 ID로 주소가 조회되는지 먼저 재현한다. 공통 주소로는 같은 두 지점을 다시 검색하므로 선택한 후보 보존은 보장할 수 없다. [주소 생성 및 후보 매핑](../frontend/src/api/real/route.js) · [QR 조회](../frontend/src/api/real/qr.js)

서버에서 후보별 불투명 ID로 경로 스냅샷을 저장하고, 휴대폰에서 열 수 있는 HTTPS 상세 페이지의 절대 주소를 각 후보의 `landing_url`로 반환하는 방안을 제안한다. 화면 순위는 운행시간 필터 때문에 바뀌므로 저장 키로 쓰지 않는다. 배포 주소, 보관 기간, 만료 안내를 정한 뒤 서로 다른 키오스크 조회가 겹쳐도 같은 링크가 같은 경로를 여는지 검증한다. QR 이미지는 기존 프론트의 qrcode-generator로 그린다. 그림 생성은 오프라인으로 가능하고 휴대폰에서 상세 페이지를 열 때는 연결이 필요하다.

### B. 지하철 노선 ID

서버는 현재 차량 이름만 보존한다. SUBWAY 구간에서 제공자별 노선 이름을 위치 데이터의 정규 ID로 변환해 `steps[].line_id: string | null`을 추가한다. “수도권 3호선”은 `seoul-3`, “공항철도”는 `arex`로 맞춘다. 다른 지역의 동명 호선과 미등록 노선은 추정하지 않는다. 프론트는 이미 서버 ID를 우선하고 일부 이름을 자체 변환한다. 두 제공자의 예시로 위치 ID와 일치하는지 검사한다. [위치 ID 원본](../kb/station_lines.py) · [화면 변환](../frontend/src/api/real/routeLegs.js)

### C. 버스 종류

카카오 파서는 `vehicles[].name`만 읽는다. 현재 코드로는 원본 `type`의 숫자·문자 여부와 의미를 확정할 수 없다. 원본 차량별 이름·타입 쌍을 확보해 대응을 확인한다. ODsay는 독립된 숫자 코드표를 쓰므로 별도로 변환한다. [카카오 파서](../server/kakao_transit.py) · [ODsay 코드표](../server/odsay_transit.py)

공개 필드 `steps[].bus_type`은 프론트가 이미 읽는 문자열 또는 null을 제안한다. 간선→TRUNK, 지선→BRANCH, 광역→EXPRESS, 순환→CIRCULAR, 마을→VILLAGE, 심야→NIGHT, 공항→AIRPORT. 경기 일반·좌석·직행은 각각 GG_GENERAL·GG_SEAT·GG_DIRECT를 유지한다. 이는 화면 계약이며 카카오 원본 코드표는 아니다. 현재 화면은 괄호 조건이 없는 첫 버스를 우선하므로 복수 후보에서 같은 번호의 타입을 골라야 한다. 번호별 종류가 다르고 대표 차량을 특정할 수 없으면 null로 둔다. 공항·심야는 현재 색상 정책상 종류를 알아도 회색이다.

### D. 도착 출구

경로에 `exit: string | null`을 추가하고 프론트의 고정 `exit: null`을 응답값으로 연결한다. 원본에서 마지막 지하철 하차 후 목적지 쪽으로 나가는 출구를 우선 확인한다. 구조화 값이 없으면 마지막 도보 안내에서 단일 출구가 명확한 사례만 추출한다. “6번 출구”는 “6”, 승차·환승 출구만 있거나 버스로 마지막 하차한 경우는 null로 검수한다.

### E. 마지막 도보

서버의 도보 계약은 `type: WALKING`과 `duration_seconds`이며 프론트에서 WALK와 분으로 변환한다. 카카오는 원본 구간을 전달하고 ODsay는 거리·시간이 모두 0인 도보를 생략한다. 마지막 도보가 제공되면 순서와 시간을 보존한다. 누락 시 시간까지 항상 제공하려면 하차 좌표와 목적지 사이의 보행 경로 조회가 별도로 필요하다. 그 전에는 미상으로 두고, 명시적인 0초는 화면의 최소 1분 처리와 구분한다. 마지막 도보 120초·0초·구간 누락을 각각 검수한다.

### F. 실제 호출 검증

검토 환경에 `KAKAO_REST_API_KEY`가 설정되어 있지 않아 실호출 결과는 미확인이다. 프론트 모의 예시는 실측 근거에서 제외했다. 키가 설정된 환경에서 `provider=kakao`로 직행 버스, 지하철, 버스·지하철 환승 경로를 조회해 각 후보의 원본과 변환 결과를 대조한다.

- **정거장 수 (#7)** 승차·하차를 포함한 전체 정차 목록일 때만 목록 길이에서 1을 뺀다. 각 구간의 양 끝, 중간 정차 목록, 실제 노선의 정거장 수를 기록한다. 특히 ODsay는 중간 목록이 없으면 양 끝 이름으로 대체하므로 두 이름만으로 1정거장이라고 표시할 수 없다. 명시적인 구간 정거장 수를 검증해 우선 사용하고, 불완전한 목록은 미상으로 전달해 프론트의 자동 계산도 막는다.
- **환승 수 (#8)** 각 후보에 카카오 원본 transfers, BUS·SUBWAY 구간 수, 그 수에서 1을 뺀 값(최소 0)을 나란히 기록한다. 차량 대안 여러 개는 한 구간으로 센다. 서버는 원본 transfers로 정렬·안내하고 화면은 구간 수로 계산한다. 불일치 여부는 아직 열려 있으며 표본이 모두 같아도 전체 경로의 보장은 아니다. 차이가 확인되면 해당 경로를 회귀 예시로 남기고 화면도 서버 transfers를 사용하도록 맞춘다. ODsay의 환승 수는 제공자의 버스·지하철 탑승 횟수 합에서 1을 뺀 별도 계산이다.
